## 1. PEAS

| Component | This agent |
|---|---|
| **Performance measure** | Answers the question correctly; selects the appropriate tool on the first try; grounds the final answer in the observation actually returned rather than inventing one; reports tool errors honestly; terminates within the 5-step budget. |
| **Environment** | A single natural-language question per episode, plus three bounded resources: a restricted Python expression evaluator, the `data/` directory (two text files), and a 12-entry in-memory knowledge base. Fully observable, deterministic, episodic — no state carries between questions. |
| **Actuators** | Three actions — `calculator(expression)`, `file_reader(filename)`, `lookup(query)` — plus the terminal action of emitting `final_answer`. The action is expressed as a JSON object; the Python loop is what actually executes it. |
| **Sensors** | The user's question, and the `Observation:` string appended to the conversation after each tool call. The agent perceives nothing else — it cannot list the directory or enumerate the knowledge base. |

## 2. Tool design decisions

**`calculator` and the `eval` tradeoff.** The tool evaluates expressions with
`eval(expression, {"__builtins__": {}}, allowed)`, where `allowed` is the
public contents of `math` plus a short list of numeric builtins (`round`,
`abs`, `sum`, `min`, `max`, `pow`, `int`, `float`, `len`). The gain is
coverage for one line of code: operator precedence, parentheses, floats and
every `math` function work immediately, and `round` in particular is needed
for questions phrased "rounded to 2 decimal places". The cost is that this is
a denylist mindset applied to a language designed for introspection — with
`__builtins__` stripped, `__import__` and `open` are unreachable, but the
approach is only as safe as my confidence that no reachable object exposes a
path back to them. A dedicated parser (`ast.literal_eval` is too narrow; a
grammar over `+ - * / ** ()` and named functions is the real alternative)
would be an allowlist by construction and could not be argued out of. For a
lab with a trusted operator the `eval` version is the right call; for anything
taking untrusted input it is not.

**`file_reader` and confinement.** The starter version joins the filename onto
`data/` and opens it, which means `file_reader("../.env")` hands the model the
API key. The version here calls `os.path.realpath` on the joined path and
rejects anything whose `commonpath` with `data/` is not `data/`, which closes
both `../` traversal and absolute paths. The interface stays a bare filename
rather than a path, so the model never needs to reason about directories.

**`lookup` and match order.** Matching is substring containment, which is
crude but predictable and needs no dependencies. The one real bug it invites:
with unordered iteration, the two-character key `"ub"` matches inside
"University at Buffalo" — and inside "b**ub**ble" — and can shadow the more
specific `"university at buffalo"` entry. The fix is to test keys longest-first,
so the most specific entry that matches wins.
